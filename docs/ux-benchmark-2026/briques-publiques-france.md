# Briques publiques françaises : ce qui peut servir le pilote travaux

**Vérification documentaire du 14 novembre 2026, sources primaires uniquement.** Les offres hébergées, le code libre et les composants commerciaux sont distingués. Cette recherche n’installe aucun outil supplémentaire et ne change pas la direction déjà validée : **AFFiNE intégré au produit Travaux, avec pages/blocs/bases natives, lecture des mails autorisés, mémoire chantier et validation humaine**. Grist reste une possibilité d’adaptateur futur, pas une troisième interface à faire apprendre au père.

La proposition d’un futur ERP municipal mérite une étude métier séparée. Aucun élément vérifié ne permet d’affirmer que « 80 % sont déjà faits » ou qu’un ERP municipal n’existe pas. Des applications publiques ou communautaires couvrent déjà plusieurs métiers ; leur assemblage ne produit pas automatiquement un système cohérent, maintenu et conforme.

## LaSuite numérique et Suite territoriale : accès différents

LaSuite numérique est portée par la DINUM ; la Suite territoriale est proposée par l’ANCT et l’ANSSI, en partenariat avec la DINUM. Il faut raisonner par **produit, instance et public autorisé**, même lorsqu’un bouton ProConnect est commun. [Présentation LaSuite](https://beta.gouv.fr/startups/suite-numerique.html), [présentation territoriale](https://suiteterritoriale.anct.gouv.fr/services).

Le dispositif territorial cite les communes de moins de 3 500 habitants, les EPCI de moins de 15 000 habitants et l’accès via structure de mutualisation partenaire. L’ANCT invite à vérifier l’éligibilité de chaque collectivité. Le pilote ne suppose donc ni l’éligibilité directe de Plougastel à une offre gratuite, ni une relation contractuelle déjà établie. [Conditions et FAQ territoriales](https://suiteterritoriale.anct.gouv.fr/services), [communiqué ANCT du 28 avril 2026](https://anct.gouv.fr/espace-presse/lancement-officiel-de-la-suite-territoriale).

ProConnect peut convenir à un SaaS pour agents publics. Il reste nécessaire de raccorder l’application, de contrôler l’organisation de l’utilisateur et d’appliquer les droits du service : une connexion réussie ne doit pas ouvrir tous les chantiers. La documentation territoriale insiste notamment sur l’adresse professionnelle et les annuaires locaux. [Règles d’intégration](https://partenaires.proconnect.gouv.fr/docs/fournisseur-service/eligibilite_installation), [prérequis territoriaux](https://suiteterritoriale.anct.gouv.fr/services/proconnect).

## Docs : bon éditeur collaboratif, pas clone Notion complet démontré

Le dépôt Docs est un projet conjoint DINUM/ZenDiS. Son périmètre publié porte sur l’écriture collaborative, la connaissance et les sous-documents. La page produit parle de partage, export et assistance à la rédaction ; elle n’établit pas une parité avec les bases relationnelles d’un workspace Notion. **Conclusion de cette recherche : Docs seul ne satisfait pas la demande de clone complet vérifiée ici.** [Dépôt officiel](https://github.com/suitenumerique/docs), [page produit](https://lasuite.numerique.gouv.fr/produits/docs).

Les licences doivent être lues à trois niveaux :

| Périmètre | Licence actuellement publiée | Conséquence pour l’étude |
|---|---|---|
| Code du projet Docs | **MIT**. [LICENSE](https://github.com/suitenumerique/docs/blob/main/LICENSE). | Ne pas reprendre l’affirmation « Docs est AGPL » comme une donnée actuelle. |
| Majorité de BlockNote | **MPL-2.0**, selon son propre dépôt. [BlockNote, section Licence](https://github.com/TypeCellOS/BlockNote#license-). | Le MIT du projet Docs ne transforme pas les licences des dépendances. |
| Paquets BlockNote XL | **GPL-3.0**, ou licence commerciale si les obligations GPL ne conviennent pas. [Même source primaire](https://github.com/TypeCellOS/BlockNote#license-). | Le README Docs prévoit `PUBLISH_AS_MIT=true` pour exclure les fonctionnalités concernées, notamment certains exports avancés. Cela ne dispense pas d’un inventaire des dépendances et fonctionnalités réellement embarquées. [Avertissement Docs](https://github.com/suitenumerique/docs#self-hosting). |

Docs dispose d’une API « resource server » avec activation OIDC et liste explicite d’actions autorisées. Le document avertit que routes, configuration et comportements peuvent évoluer. La configuration par défaut autorise notamment lecture/liste/création/enfants des documents ; elle n’ouvre pas toutes les modifications ou la gestion des accès. L’intégration d’un document depuis du Markdown est illustrée. **API existante ne signifie donc pas contrat figé ni écriture arbitraire de blocs déjà éprouvée.** [Documentation resource server](https://github.com/suitenumerique/docs/blob/main/documentation/resource_server.md).

Le projet documente aussi une intégration serveur à serveur utilisée pour les transcriptions de Meet et un déploiement auto-hébergé. C’est une preuve d’interopérabilité, pas une validation de notre synchronisation de mémoire chantier. L’instance gouvernementale et une instance OVH que nous exploiterions seraient deux services distincts. [README](https://github.com/suitenumerique/docs), [installation](https://github.com/suitenumerique/docs/blob/main/documentation/installation/README.md).

## Grist : cœur réutilisable et frontières de l’édition complète

Le fichier de licence de **Grist Core est Apache-2.0**. Le dépôt présente Core comme une application serveur exploitable, pas seulement une bibliothèque de cellules. Les références relationnelles, règles d’accès et intégrations font partie de son périmètre. L’organisation **Grist Gouv** rassemble des widgets maintenus ou audités par les équipes DINUM/ANCT ; cela ne change pas l’origine ni la licence de l’upstream. [Licence Core](https://github.com/gristlabs/grist-core/blob/main/LICENSE.txt), [Grist Gouv](https://github.com/gristgouv/).

Le README actuel distingue du cœur l’édition complète : stockage Azure spécifique, audit log streaming, contrôles d’administration avancés, assistant étendu, notifications, automations, applications OAuth et serveur MCP intégré. Ne pas budgéter ces fonctions comme acquises dans `grist-core`. Un adaptateur REST ou un serveur MCP externe reste un développement distinct. [Comparaison officielle dans le dépôt](https://github.com/gristlabs/grist-core).

Les accès de document sont décrits par rôles propriétaire/éditeur/lecteur, puis affinés par règles sur les tables, colonnes et lignes. Les conditions peuvent s’appuyer sur l’utilisateur, l’enregistrement et la valeur proposée. Leur existence ne dispense pas de tester une fuite entre deux services ou deux collectivités. [Règles d’accès](https://support.getgrist.com/access-rules/).

Grist documente REST, widgets personnalisés et affichage embarqué. Le tutoriel d’embed commence avec un document public ; son paramètre visuel ne constitue pas une solution d’authentification privée. Les widgets ont des droits pouvant aller de zéro accès à la lecture/écriture du document entier : un widget externe peut donc devenir une sortie de données. Pour notre cas, widgets et scripts éventuels seraient servis dans le périmètre contrôlé, et les droits testés. [API REST](https://support.getgrist.com/api/), [embed](https://support.getgrist.com/embedding/), [permissions des widgets](https://support.getgrist.com/widget-custom/#access-level).

**Décision proposée : ne pas ajouter Grist au pilote actuel.** Si une mairie l’utilise déjà ou si de futurs référentiels structurés le justifient, créer un adaptateur sur les identifiants canoniques du domaine Travaux. Choisir alors explicitement quel système possède chaque donnée, quels champs sont éditables et comment traiter les conflits. Deux tables synchronisées sans responsable de chaque champ ne constituent pas une architecture métier.

## Albert : instance publique et passerelle auto-hébergée sont deux options

La page actuelle de la DINUM renvoie vers **`etalab-ia/OpenGateLLM`**, sous MIT. Le lien historique `etalab-ia/albert-api` a retourné 404 lors de cette vérification. OpenGateLLM est une API gateway ; son README annonce aussi une API encore en bêta avec ruptures possibles. [Produit DINUM](https://ia.numerique.gouv.fr/outils-ia/albert-api/), [dépôt et licence](https://github.com/etalab-ia/OpenGateLLM).

L’accès hébergé ne peut pas être promis au père : le guide annonce l’accès automatique par ProConnect pour les agents de la **fonction publique d’État**, et la page contact précise cette réserve. La fonction publique territoriale et un futur éditeur privé ne sont pas réputés automatiquement autorisés. Une extension d’accès éventuelle doit être confirmée pour le service concerné avant d’en faire une dépendance. [Guide Albert](https://guides.ia.numerique.gouv.fr/albert-api), [contact/éligibilité](https://ia.numerique.gouv.fr/outils-ia/albert-api/albert-api-contact/).

Pour auto-héberger OpenGateLLM, les exemples officiels prévoient notamment PostgreSQL, Redis, la passerelle et un playground. Le fichier de configuration raccorde des fournisseurs d’inférence, par exemple vLLM ; il ne fournit pas un modèle prêt à tourner gratuitement. Il faut encore choisir les modèles et leurs licences, les serveurs d’inférence, la capacité matérielle adaptée au débit, l’identité, les secrets et l’exploitation. Les exemples ne sont pas à recopier comme configuration de production : ils utilisent entre autres des valeurs de démonstration et des images non figées. [Compose officiel](https://github.com/etalab-ia/OpenGateLLM/blob/main/compose.example.yml), [configuration officielle](https://github.com/etalab-ia/OpenGateLLM/blob/main/config.example.yml).

**Albert hébergé, OpenGateLLM sur OVH et un modèle Mistral sont trois objets différents.** Les annonces de sécurité de l’instance de l’État ne couvrent pas notre serveur. L’ANSSI précise qu’une offre ne peut pas hériter automatiquement d’une qualification SecNumCloud parce qu’elle utilise une offre qualifiée ; la sécurité de l’application cliente reste à examiner. [FAQ ANSSI](https://cyber.gouv.fr/enjeux-technologiques/cloud/faq-qualification-secnumcloud/).

## openMairie : reprendre du métier concret, pas seulement des noms de modules

Le **framework officiel** est une bibliothèque PHP/générateur. Son `LICENSE.txt`, lu directement dans le dépôt GitLab le 14 novembre 2026, indique **GPL version 3 ou ultérieure**. Son intérêt est de générer formulaires, listes, éditions et affichages à partir d’un modèle de données. Ce n’est pas un moteur de règles municipales universel. [Dépôt](https://gitlab.com/openmairie/framework-openmairie), [fichier de licence](https://gitlab.com/openmairie/framework-openmairie/-/raw/master/LICENSE.txt).

Le forum communautaire référence réellement openADS (instruction du droit des sols), openARIA (sécurité/accessibilité des **établissements recevant du public**), openCimetière, openCourrier, openDébitDeBoisson, openElec et openRésultat. Le sigle ERP d’openARIA désigne ici un établissement recevant du public, pas un progiciel de gestion intégré. Ces applications ont des périmètres et versions propres. [Catalogue communautaire primaire](https://communaute.openmairie.org/).

Pour **openCourrier**, la fiche de forge indexée annonce GNU GPL et une publication 5.1.1 le **4 mars 2022**. La documentation 5.0 décrit notamment pièces de type arrivée/départ/pièce jointe, dates, observations et notion d’affaire pour les liens complexes. La version exacte du texte de licence de l’archive choisie reste à contrôler avant reprise de code ; la fiche générique « GPL » ne suffit pas à attribuer automatiquement GPL-3.0 à toutes les applications. Les dates des annonces ne permettent pas, à elles seules, de conclure à un abandon. [Forge](https://adullact.net/projects/opencourrier/), [documentation 5.0](https://app.readthedocs.org/projects/opencourrier/downloads/pdf/5.0/).

Pour **openVoie**, la fiche décrit un périmètre utile, mais son statut Alpha et son ancien jalon documentaire ne permettent pas de le recommander comme moteur prêt à déployer. Une API actuelle, un support assuré ou une conformité réglementaire à jour n’ont pas été établis par cette recherche. [Fiche primaire](https://www.adullact.net/projects/openvoie/).

La reprise utile aurait trois formes clairement différentes :

1. **Étude métier** : examiner objets, états, responsabilités, relations courrier/affaire/service et cas limites, puis confronter ces règles au fonctionnement réel de la mairie. Nommer une table « marchés publics » n’implémente pas une procédure.
2. **Interopérabilité** : si un outil existe déjà, utiliser un export ou une API réellement constaté et conserver ses identifiants ; ne pas inventer une interface parce que le code est libre.
3. **Réutilisation de code** : figer la version, relever licences et notices, analyser dépendances et sécurité, puis conserver les obligations applicables. Une « réécriture par IA » n’est ni une preuve de droits suffisants ni une preuve de fidélité métier. La DINUM recommande de vérifier les licences dans les dépôts et d’évaluer aussi fonctions, sécurité et communauté. [Guide officiel code.gouv.fr](https://code.gouv.fr/documentation/).

Les vraies données municipales, mails et fichiers d’usagers ne deviennent pas des données ouvertes parce que le logiciel est libre. Pour cette étude, aucun dossier réel n’a été importé ni aucun service externe contacté.

## Ordre d’intégration recommandé

**Maintenant :** terminer le pilote du responsable travaux avec un seul espace natif AFFiNE, lecture des messages autorisés, rattachement chantier, notes humaines, propositions sourcées et récapitulatif approuvé. Les composants publics ci-dessus éclairent les choix sans ajouter des connexions fictives ou des interfaces concurrentes.

**À la première validation DSI :** identifier l’identité de référence et les services publics déjà accessibles ; confirmer les contrats d’accès, les périmètres de données et les interfaces. Étudier ProConnect sans le confondre avec une autorisation métier.

**Après usage terrain concluant :** choisir un seul besoin d’extension démontré — par exemple interventions terrain, référentiel Grist ou publication Docs — et réaliser un adaptateur avec retour arrière et tests d’accès. Aucun pourcentage de réutilisation n’est sérieux avant cette cartographie de besoins et de capacités.

## Limites précises de la vérification

Les dépôts et documentations consultés prouvent les périmètres publiés, pas leur qualité en production à Plougastel. Aucune instance de ces nouveaux outils n’a été installée. Certaines pages openMairie ont renvoyé des erreurs de disponibilité et la forge a parfois présenté un blocage anti-robot : la recherche s’est limitée aux pages primaires indexées, documentations publiques et fichiers publics accessibles, sans contournement. Aucune API métier openCourrier/openVoie n’a été testée et aucune licence précise d’archive applicative non lue n’est présentée comme confirmée.
