# ERP et agents : briques vérifiées, périmètre raisonnable

Recherche sur sources primaires, vérifiée le **14 novembre 2026**. Cette note compare des possibilités d'intégration ; **aucun ERP ni connecteur ci-dessous n'a été installé ou raccordé par cette étude**. Le pilote porte sur le suivi des travaux du père de l'utilisateur. Une gestion complète de mairie, un guichet usager ou l'état civil demanderaient leurs propres processus, droits, règles et logiciels spécialisés.

**Recommandation : garder un seul cœur métier et une API qui contrôlent projets, sources, faits, notes, décisions et versions.** Le moteur documentaire retenu sert l'édition ; un ERP éventuel se raccorde ensuite sur un besoin mesuré. Installer simultanément Frappe, Odoo, Twenty, Grist et AFFiNE créerait plusieurs modèles de droits, de données et de synchronisation avant d'avoir validé le premier parcours.

**Point de protocole :** MCP fournit des outils à un client/agent ; une API d'inférence Mistral reçoit des messages et produit une réponse. Ce sont deux contrats différents. Une mention « BYO-LLM » n'empêche aucun transfert vers un modèle externe si ce modèle est justement configuré à l'extérieur. ## Odoo Community, IA native et OCA : frontière à conserver

La documentation Odoo 19 décrit une application IA avec agents, prompts, contexte de l'enregistrement et automatisations. Ce sont des capacités de l'offre documentée, **pas une preuve qu'un téléchargement CE les contient**. Les vérifications publiques `addons/ai` dans `odoo/odoo`19.0 et 20.0 ont retourné 404 ; aucune installation CE avec IA native stock n'est validée ici. Le module Enterprise correspondant n'a pas été inspecté dans un dépôt privé. [Documentation des prompts](https://www.odoo.com/documentation/19.0/applications/productivity/ai/default_prompts.html), [IA support](https://www.odoo.com/documentation/19.0/applications/productivity/ai/support_operations.html), [dépôt CE19](https://github.com/odoo/odoo/tree/19.0/addons).

En conséquence, pour un scénario entièrement communautaire, budgéter **une intégration OCA ou dédiée**, son modèle, son endpoint et ses tests. Ne pas chiffrer la solution comme si les agents IA Enterprise, Studio, Helpdesk et tous les modules montrés dans les démonstrations étaient présents dans CE. À l'inverse, le JSON-2 Community vérifié ne doit pas être décrit comme une fonction exclusivement Enterprise.

## Architecture recommandée et étape de décision

Pour le pilote actuel : conserver l'API métier du suivi travaux, le connecteur de lecture institutionnel autorisé, les originaux immuables, les propositions révisables et le moteur d'édition natif retenu. Le LLM propose ; les mutations passent par les commandes du serveur, avec version attendue et journal. Aucune bibliothèque d'agents n'est nécessaire tant qu'une extraction et une génération structurées suffisent.

Si un besoin ERP apparaît, choisir **un** candidat sur un mini-scénario réel : matériel affecté à un chantier, demande d'intervention, commande fournisseur ou suivi d'un prestataire. Frappe est mon premier candidat à expérimenter pour un modèle métier très personnalisé ; OdooCE est une alternative si modules/intégrateur existants apportent davantage ; Twenty vise surtout la relation/interlocuteur. Ce classement est notre jugement d'architecture, pas une performance comparative mesurée.

Avant de retenir un composant : figer tag/commit et licence, démontrer lecture des métadonnées avec un compte limité, prouver refus d'un autre tenant/périmètre, créer un brouillon et le revoir humainement, rejouer une commande sans doublon et exporter les données. Le test doit fonctionner avec un faux modèle puis un endpoint privé déterminé ; les exemples Claude/ChatGPT des README ne constituent pas une autorisation d'y envoyer les données de la mairie.

Pour le futur SaaS : le portail de configuration exploitant manipule des références de secrets et l'état des capacités, jamais leurs valeurs dans l'interface utilisateur ou les journaux. Les données réelles restent soumises au périmètre autorisé et aux décisions DSI/DPO. Une base vectorielle, une API, du RAG ou un ERP open source ne constitue pas un certificat RGPD.

Une release récente prouve une activité, pas une assurance de qualité ou de maintenance future. Non testés ici : déploiement de ces ERP, permissions effectives d'une instance, pont Mistral/Raven/FAC, synchronisation métier bidirectionnelle, migrations et localisation municipale française. Aucun accès aux secrets de déploiement n'a été nécessaire à cette recherche.
