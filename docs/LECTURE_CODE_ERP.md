## 1. ERPNext / Frappe : des protections concrètes, un rattachement heuristique

Le [contrôleur Issue](https://github.com/frappe/erpnext/blob/8e10a348daaa93853de8c36dc55ec789a440c219/erpnext/support/doctype/issue/issue.py#L77) restaure les champs réservés aux agents lorsqu’une demande provient du portail/formulaire web. Il force aussi l’auteur d’une nouvelle demande web à l’utilisateur de session. Cette protection est utile précisément parce que le formulaire emploie un chemin avec permissions contournées. Le [schéma Issue](https://github.com/frappe/erpnext/blob/8e10a348daaa93853de8c36dc55ec789a440c219/erpnext/support/doctype/issue/issue.json) définit ses champs, statuts et rôles ; ce n’est pas un simple formulaire dessiné dans un README.

`set_lead_contact` recherche un prospect ou contact par adresse email, puis son éventuel client. **Cela rapproche des identités ; cela ne prouve ni l’identité de l’expéditeur ni son droit de modifier un chantier.** Les vues portail filtrent ensuite les demandes selon l’auteur et les clients liés au contact. Le [moteur de permissions](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L81) tient compte du contexte utilisateur et des permissions de document/rôle ; le compte Administrator possède une branche privilégiée. Lire cette entrée ne suffit pas à déclarer tous les chemins du framework audités.

La [réception email](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/email/receive.py#L767) déduplique à partir de `Message-ID`, du compte et du sens du message. Le [rattachement](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/email/receive.py#L805) cherche d’abord le parent via `In-Reply-To`, puis la référence de document. En secours, [`match_record_by_subject_and_sender`](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/email/receive.py#L878) rapproche référence dans l’objet, objet et expéditeur, avec une fenêtre de 60 jours. Une exception permet l’objet seul pour un utilisateur interne et un objet dépassant dix caractères. **Ce secours reste une heuristique : ne pas le copier comme affectation silencieuse aux chantiers.**

Application à Travaux : protéger les champs validés côté serveur, utiliser les identifiants de fil avant les rapprochements de texte, présenter les ambiguïtés à un agent. Ces fichiers dépendent de `frappe.db`, des sessions, DocTypes et hooks Frappe : leur copie dans FastAPI ne constitue pas une intégration fonctionnelle. Une adoption future devrait être une application Frappe avec permissions et migrations testées.

## 2. Twenty : exécuter une version identifiée dans un espace identifié

Le [`workflow-trigger.job.ts`](https://github.com/twentyhq/twenty/blob/bd8ab939f0e238b5faeefcbeb897ecd6862b1a59/packages/twenty-server/src/modules/workflow/workflow-trigger/jobs/workflow-trigger.job.ts#L37) distingue deux formats de dispatch, vérifie que la version appartient au workflow et au workspace, exige une version active, puis vérifie la cohérence d’un éventuel identifiant de version historique. Un dispatch incohérent est journalisé et transmis au gestionnaire d’exceptions ; il ne lance pas arbitrairement la dernière définition disponible.

Le [`run-workflow.job.ts`](https://github.com/twentyhq/twenty/blob/bd8ab939f0e238b5faeefcbeb897ecd6862b1a59/packages/twenty-server/src/modules/workflow/workflow-runner/jobs/run-workflow.job.ts#L41) choisit démarrage, reprise, réessai ou fin d’étape attendue. Il exécute dans un contexte workspace construit pour le système. Au démarrage, il refuse les statuts inattendus et vérifie la version ; le réessai remet à zéro seulement les étapes considérées comme en attente de réessai. Une erreur système termine le run en échec puis est relancée. Les autres services importés n’ont pas tous été inspectés : ces deux jobs ne prouvent pas à eux seuls l’isolation complète de la pile.

Application à Travaux : lier chaque traitement à une version de contexte et de règles, conserver le run, l’erreur et les étapes, traiter explicitement les réessais. **Un moteur de workflow n’apporte pas automatiquement la validation humaine d’une proposition IA.** Ajouter Twenty imposerait ici son ORM, ses services de workflow, sa file de messages et son contexte de permissions. Reporter cette dépendance ; examiner licence et éventuelles limites d’édition sur les fichiers réellement repris avant toute distribution.

## 3. OCA ai_oca_bridge : un pont HTTP Odoo, pas un moteur de vérité

Le [`ai_bridge.py`](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/models/ai_bridge.py) configure une destination HTTP, des modes d’authentification, des usages et une préparation de payload. Les champs d’authentification sont réservés au groupe système. Le [`ai_bridge_execution.py`](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/models/ai_bridge_execution.py#L113) poste ce JSON vers la destination configurée, conserve réponse/erreur et passe l’exécution à `done` ou `error`. Le délai HTTP par défaut est de 30 secondes, surchargeable. Le mode asynchrone crée une échéance et une URL de retour avec jeton HMAC.

Le [contrôleur de rappel](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/controllers/ai.py) est publiquement accessible, désactive CSRF et lit l’exécution en `sudo()`, **mais vérifie un jeton en temps constant et son échéance** avant de traiter la réponse. Cette combinaison exige une revue des jetons, journaux, relectures et destinations HTTP ; ce constat ne suffit pas à déclarer une faille. Le traitement de réponse peut publier un message Odoo ou retourner une action. Ce n’est pas un contrat natif de faits sourcés soumis à l’approbation d’un responsable.

Les [droits d’accès](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/security/ir.model.access.csv) et [règles de société](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/security/security.xml) distinguent lecture utilisateur et configuration système. Le [manifeste](https://github.com/OCA/ai/blob/7490c3c1286a35ca240a5ab0d5b768cfeecb6365/ai_oca_bridge/__manifest__.py) annonce AGPL-3. La conformité de toutes les opérations multi-sociétés n’a pas été testée.

Application à Travaux : reprendre l’idée de run traçable avec rappel borné, tout en conservant un schéma de sortie strict, les sources et l’approbation. Ce pont accepte une URL ; il ne garantit ni Mistral, ni traitement en France, ni absence d’entraînement fournisseur. La configuration, les contrats et le déploiement restent à vérifier.

## Limites de cette lecture

Les assertions ci-dessus viennent des fichiers d’implémentation cités, pas d’une démo commerciale. Aucun test amont n’a été exécuté ; les connecteurs Exchange, les garanties contractuelles, l’ensemble des dépendances et les obligations métier d’une mairie restent hors de ce contrôle ciblé. Aucun pourcentage de « code déjà fait » ou de couverture d’un ERP municipal n’est déduit de ces lectures.
